# 統合イベントカレンダー Phase 2 設計（こんぴらカレンダーの行事を Notion に登録する）

- 作成: 2026-11-05（会話セッション）
- 前提: Phase 1 実装済み（multi-select「カレンダー」・レイヤー切替・金刀比羅宮61件）。誌面CSV `assets/towncal/events-YYYY-MM.csv` は日曜の週次ランが自動で作る（`scripts/towncal_csv.py`・check 列つき）。重複防止の規則は `docs/重複防止_設計.md`（登録スキルは同日類似を保留）
- 状態: **設計（実装は同日に着手）**

## 1. 方針の変更（v1.0 からの差）

v1.0 は「最初の2〜3か月は半自動（人の承認必須）」だった。これを**自動登録＋事後確認**に変える。理由は3つ。

1. サイトの「こんぴらカレンダー」レイヤーは**初期 OFF**で、ホームの直近イベントにも出ない。転記の誤りがあっても、本人が ON にするまで誰にも見えない
2. 本人の運用方針は「毎週勝手にやって欲しい。黒い窓も確認の手間も無し」。月35件を毎月目で承認する工程は続かない
3. 直す場所は Notion の該当ページ1か所。CSV の段で直させても二重になる

本人の判断が要るのは「同日に似た既存の行事がある」ときだけで、それも**既定の処理（既存ページに値を足す）**を自動で行い、結果を報告する。

## 2. 流れ（日曜の週次ラン）

```
run_weekly.bat
  git pull kotohira-news
  towncal_csv.py       … 新しい号の CSV を作る（既存）
  towncal_register.py  … CSV のうち未登録の号を Notion に登録する（新規）
```

`towncal_register.py` の対象は「`events-YYYY-MM.csv` があり `events-YYYY-MM.registered.json` が無い号」（2026-10 以降）。通常は月1回。

## 3. 1行 → Notion イベントの対応

| CSV | Notion |
|---|---|
| title | イベント名 |
| date（＋time があれば先頭の時刻） | 開催日時（開始）。時刻は `YYYY-MM-DDTHH:MM+09:00`。time が「10:00〜12:00」なら 10:00 を開始、12:00 を 開催日時（終了）に |
| place | コメントに「場所: …」。「開催場所」relation は送れない（既存の制約） |
| booking / note / category | コメントに「要予約」「備考: …」「区分: …（誌面の色分けから推定）」 |
| source | コメント末尾に「出典: 広報ことひら YYYY年M月号 こんぴらカレンダー」。ソース列には町HPの広報一覧 URL（`towncal-data.js` の sourceUrl） |
| check=1 | コメント先頭に「【要確認】誌面の読み取りに自信がない行」 |
| （固定） | 市町村＝琴平町、カレンダー＝`こんぴらカレンダー`（config の既定） |

- 可燃ごみ臨時収集・訓練放送（全国一斉緊急地震速報訓練・Jアラート）も登録する（町民向けの予定として誌面にあるものは全部。レイヤーが OFF なら見えない）
- 「○月の相談日」の表・納期・統計は CSV の段で既に除いている

## 4. 重複の扱い（登録スキルの同日類似）

- 登録は `register_news.py --config config-events-towncal.json`（新規 config。既定の カレンダー＝`こんぴらカレンダー`、dedup_mode＝title_date、同日類似は保留）
- 結果が **保留（同日類似）** の行: 新規作成しない。代わりに**既存ページに `こんぴらカレンダー` を和集合で足す**（`patch_calendar_values.py` と同じ処理を内蔵）。一致率 0.9 以上または内包のときだけ自動で足し、0.8〜0.9 は足さずに報告だけ（人が見る）
  - 例: 本人が登録済みの「こんぴら朝市」と誌面の「こんぴら朝市」→ 既存に値を足す＝1件が 基本＋こんぴらカレンダー になる（狙いどおり）
- 結果が **重複スキップ（題名と日付が一致）** の行: 既存ページに値を足す（同上）
- 新規作成した行は `カレンダー＝こんぴらカレンダー` のみ。**町外の人も来られる行事に `基本のイベント` を足すのは本人が Notion で行う**（判断は人。報告に候補の印を付ける: 題名に 朝市／マルシェ／祭／体育祭／図書館一般開放／マラソン を含む行）

## 5. 記録と報告

- `assets/towncal/events-YYYY-MM.registered.json`: 行ごとの結果（created / tagged_existing / held / skipped・page_url・一致率・既存ページ）。これが「登録済み」の印（二重登録の防止）
- `assets/towncal/events-YYYY-MM.registered.md`: 人が読む表（登録 n件・既存に付与 n件・要判断 n件・要確認 n件、基本のイベント候補の印）
- 日曜のレポート（`YYYY-MM-DD_sns-drafter-weekly_plan.md`・hisho-bot が Discord に中継）に1行: 「🗓 こんぴらカレンダー 11月号: 登録 30・既存に付与 3・要判断 2（詳細は kotohira-news assets/towncal/events-2026-11.registered.md）」
- commit・push は CSV と同じ方式（`git pull --rebase --autostash` → push。未 push の再試行つき）

## 6. 初回（2026-10・11 号）

- 10月号は過去の行事が多い（終了済み）。終了から60日を超えるとサイトには出ないが、Notion の記録としては登録する（統合カレンダーの正本は Notion）
- 初回だけは本人の「登録して」を待つ。実行前に dry-run の結果（新規・既存に付与・要判断の件数と一覧）を会話で見せる。12月号からは自動
- 既存との重なりの見込み: 10月号＝こんぴら朝市 10/25・石段マラソン 10/4・街ガチャ 10/23、11月号＝こんぴら朝市 11/8・こんぴらマルシェ 11/22・町民体育祭 11/1 あたり（本人や bot が既に登録していれば「既存に付与」になる）

## 7. 守ること

- 登録スキルの dry-run → 本実行の順を守る（初回は本人承認、以後は自動）
- 消さない。既存ページの値は足すだけ
- 判定に失敗したら登録を止めない（従来の方針）。claude の呼び出しは増やさない（CSV の段だけ）
- トークンは keyring 経由。.env を読まない
