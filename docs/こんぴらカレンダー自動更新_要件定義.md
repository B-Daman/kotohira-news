## 4. 要件 A: 画像の差し替え（全自動・GitHub Actions）

### 4-1. 動かし方

- **専用の workflow は作らない**。既存の毎時 `update-notion-data.yml` に1段足す（新しい周期を増やさない。本人の運用方針）
- 門（3つ全部が真のときだけ町HPを見る）: (1) 今日が **20日以降** (2) その回が **09:00 JST** の実行 (3) `issues[]` に**翌月の号がまだ無い**。どれか偽なら1秒で抜け、ネットワークには出ない
- 翌月号を保存した時点で (3) が偽になり、**その月はもう町HPを見ない**（本人「取得できたらその月はもう動かさない」）。月あたりの実アクセスは最大12回（20〜31日の09:00）、通常は公開日までの数回
- 公開が遅れた月は翌月20日以降の回で拾う（最大約3週間、前の号の面が出続ける）。急ぐときは手動起動（workflow_dispatch）。**1〜7日の保険は置かない**
- 翌月号は前月の20日過ぎに出るので、**翌月分の画像は前月末までに入る**のが通常

### 4-2. スクリプト（`fetch_towncal.py` に `--auto` を足す。既存の手動の使い方は残す）

1. 広報一覧ページを取得し、リンク文字列 `広報ことひら(\d{1,2})月号` を全部拾う。年は号のページの `(\d{4})年(\d{1,2})月号` から決める（一覧に年が無いため）
2. 最新の号の年月が `TOWNCAL.month` 以下なら終了（出力1行「新しい号なし」）
3. 号のページから PDF/画像のリンクを拾う。リンク文字列に「カレンダー」を含む個別ファイルがあればそれを使う（ページ指定なし）。無ければ全ページ一体の PDF を使う
4. 一体 PDF のとき、ページの本文が **「こんぴらカレンダー」と「相談日」の両方を含むページ**を探す。見つかったページが1つならそれ。0 または 2 以上なら失敗（取り込まない）
5. 既存の処理（ページ画像化 → WebP 長辺1200px）を実行し、`towncal-data.js` の `issues[]` に号を**追加**する（4-4）
6. 失敗はすべて非ゼロ終了＝workflow が失敗し、GitHub の失敗メールで分かる。前回のファイルは残る

### 4-4. 表示の切り替え（翌月号が早く届くため）

- `towncal-data.js` は単一の `month/image/sourceName` から、号の一覧 `issues: [{month, image, sourceName}, …]`（新しい順）に変える。既存の3か月分（2026-09・10・11）を初期値にする
- ページ（`index.html` の towncal タブ）は**今日の年月と同じ号を表示**する。無ければ一番新しい号。翌月号が既にあれば「来月号を見る」の切り替えを出す（前月末の10日間は今月と来月の両方が見られる）
- 月が替わる瞬間に workflow は要らない（ページが日付で選ぶ）
- `sourceUrl`・`sourceLinkLabel` は号に依らず共通のまま

### 4-3. 守ること

- ダウンロード先は `www.town.kotohira.kagawa.jp` のみ（既存のガードを使う）
- 外部へ送るものは無い（取得と自リポジトリへのコミットだけ）
- PyMuPDF と Pillow は workflow 内で `pip install`。リポジトリに `requirements-towncal.txt` を1つ置く
- 画像の目視確認は人が行わなくなる。代わりに「ページ判定が一意でなければ取り込まない」を守る。誤った面を載せた月は、手動で `fetch_towncal.py <url> <月> --page N` を回して直す（既存の手順）

## 5. 要件 B: 行事 CSV の転記（半自動・日曜の週次ランに乗せる）

### 5-1. 動かし方

- sns-drafter の `run_weekly.bat`（毎週日曜 07:30・kotohira-news を `git pull` した直後）に1段足す。**新しい処理の周期は既存の週次工程に接続する**（本人の運用方針）
- 条件: `issues[]` のうち `assets/towncal/<month>.webp` があって `events-<month>.csv` が無い号があるときだけ動く＝月1回。翌月号は前月の20日過ぎに入るので、**CSV も前月末の日曜までにできる**（統合カレンダー Phase 2 の登録を月初に間に合わせられる）
- 手順: WebP を PNG に変換（一時フォルダ）→ `claude -p`（sonnet・道具は Read のみ・WebSearch/WebFetch 禁止）に誌面を読ませ、固定の列で CSV 本文だけを出させる → スクリプトが検証して保存 → kotohira-news に commit・push（Actions のコミットと衝突しないよう `git pull --rebase` の後に push）

### 5-2. 転記の規則（プロンプトに固定）

- 誌面に印刷されている行事だけを書く。推測で補わない。読めない文字は空欄にして `check` 列を 1 にする
- 列: `date,dow,title,time,place,booking,category,note,source,check`
  - `dow` は Claude に書かせず、スクリプトが日付から計算して上書きする（曜日の誤りを防ぐ）
  - `place` は凡例の略称を正式名に展開（総セ→総合センター 等。凡例は誌面にある）
  - `category` は色分けからの推定（相談／福祉・保健／その他）。判断できなければ空欄
  - 「○月の相談日」の表・納期・統計欄は転記しない（カレンダーの升目の行事だけ）
- 検証（スクリプト）: 日付が対象月の中にある・1行も無い月は失敗・行数が前月の半分未満なら `check` を全行 1 にして保存（取りこぼしの疑い）

### 5-3. 確認の位置

- CSV は下書き扱い。**本人の確認は統合カレンダー Phase 2 の Notion 登録（dry-run → 承認）のときに行う**。CSV の段階で人の作業を増やさない
- `check=1` の行は Phase 2 の承認画面で先頭に出す（Phase 2 の設計で扱う）

### 5-4. 守ること

- 誌面は町の公開物。写真ライブラリの「中身を見せない」裁定とは別（写真ではない）
- LLM の呼び出しは月1回・1往復。費用は Max の枠内（週次ドラフトと同じ経路）
- `claude -p` が失敗した月は CSV を作らず、次の日曜に再試行する（条件が同じなので自然に再試行になる）
