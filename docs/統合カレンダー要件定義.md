# 統合イベントカレンダー 要件定義

v1.0 / 2026-09-03 / 起案: あっきー・まとめ: Claude（Fable 5）

## 目的

町のイベント・金刀比羅宮の年中行事・こんぴらカレンダー（広報の町民向け予定）を1つのカレンダーに統合し、
Googleカレンダーのようにソース単位でON/OFFできるようにする。「琴平の予定は全部ここ」を実現する。

## フェーズ分割

- **Phase 1（本要件の実装範囲）**: ソース切替UI＋金刀比羅宮レイヤー
- **Phase 2（概要のみ・詳細設計は別途）**: こんぴらカレンダーの月次バッチ登録
- 対象外: キャンペーン月グリッドの統合（性質が違うため混ぜない）、右サイドバーの大型イベント告知枠（site-widgets-data.js由来でNotion非連動のため現状維持）

## データ設計

- NotionイベントDBに **select プロパティ「カレンダー」** を追加（あっきーさんがNotion UIで作成。選択肢は書き込み時に自動生成されるため事前登録不要）
  - 値: 空（既定）＝町のイベント ／ `金刀比羅宮` ／ `こんぴらカレンダー`
  - 既存イベント（約96件）は空のまま＝町のイベント扱い。**移行作業なし**
- `scripts/fetch_notion.py`: `parse_event` に `calendar`（カレンダー select）と `featured`（大規模イベント checkbox）の出力を追加。
  既存の `get_*` ヘルパーはプロパティ非存在で空を返すため、同関数を共用するキャンペーンDBにも無害（調査済み: fetch_notion.py:229, 254-258）
- konpie-bot への影響: **なし**（全て `properties.get()` 方式・未知プロパティ無視、書き込み側はDBスキーマ動的取得で既知キーのみ送信。調査済み: notion_register.py:293-300 ほか）

## 表示仕様（Phase 1）

### ソース切替チップ
- イベントタブのカレンダー上部に、月/週トグルと同じ流儀のチップ群（`data-cal-layer`、`aria-pressed`、既存 `.cal-view-btn` 系デザイン踏襲）
- チップ構成は**データ駆動**: 「📅 町のイベント」（calendar空）＋データに実在する calendar 値のみ表示（⛩ 金刀比羅宮 → 🗓 こんぴらカレンダー → 未知値の順）。
  金刀比羅宮のデータが入るまでチップ群自体を出さない＝**登録前は見た目が一切変わらない**
- 色分けは控えめに: チップに色ドット、カレンダー内は単日チップ先頭の色ドット＋複数日バーのソース色のみ。町のイベントは現行色のまま
- 詳細モーダルに、calendar 非空のときソースバッジを表示

### フィルタの効かせ方
- `visibleEvents()` アクセサを新設し、`ND.events` 直接参照の5箇所（index.html:1299, 1322, 1534-1537, 1837）を差し替える。
  以下の描画ツリーは引数渡しのため自動で追随（月グリッド／週グリッド／スマホ一覧／今日・今後カード／両モーダル）
- ホームの「直近のイベント」だけは別ルール: **町のイベント＋（金刀比羅宮のうち大規模イベント✓のみ）**。
  月次祭等の定例でカルーセル3枠が埋まるのを防ぎつつ、例大祭級はホームに出す

### 初期状態
- イベントタブ: 町のイベント=ON、金刀比羅宮=ON、こんぴらカレンダー=OFF
- レイヤー選択はページ内のみ保持（localStorage永続化はしない。入口別デフォルトとの競合を避けるため当面見送り）
- 全レイヤーOFF時は「表示中のカレンダーがありません」の案内（Notion未取得の文言と混同させない）

## 金刀比羅宮データの登録（Phase 1）

- ソース: 公式サイトの令和8年（2026年）年間行事一覧（リサーチ済み・scratchpad/konpira-events.md）
- **裏取りできた行事のみ登録**。蹴鞠（2026年一覧に無し）は載せない。毎月の月次祭4種（1・6・10・26日）は件数が膨らむ割に価値が薄いため登録しない（要望があれば追加）
- 例大祭（10/9-11・固定日程）は各神事の時間・場所まで詳細登録
- 経路: `kotohira-news-register` スキルの `register_news.py --config config-events.json`（イベントDB向け設定を新設）
  - **事前改修3点**: ①終了日（date end）送信対応 ②トークン env 名の分離（読み取り専用 `KOTOHIRA_NOTION_TOKEN` と衝突するため）③会場は「開催場所」relation非対応のためコメント欄に記載（konpie-bot前例に倣う）
  - **本登録前に必ず `--dry-run`**: 旧API（2022-06-28）でのスキーマ取得疎通を確認（DBがマルチデータソース化していると落ちる既知リスク）。落ちたら data_sources API 対応を判断
- 年次運用: 年1回（1月頃）、公式の新年度行事一覧と突き合わせて更新。**移動祝日連動の5件**（成人の日・春分・海の日・秋分・スポーツの日）は毎年日付が変わるため必ず確認

## Phase 2 概要（詳細設計は精度検証後）

- fetch_towncal.py が生成する誌面画像をClaudeが構造化 → `--dry-run` でドラフト → **誌面と突き合わせて承認 → 本登録**（カレンダー=こんぴらカレンダー タグ付き）
- 最初の2〜3か月は半自動（人の承認必須）。精度が安定したら承認を軽量化
- 誌面画像ページ（くらし > こんぴらカレンダー）は正本の忠実なコピー兼検証台帳として存続。Phase 2開始時に「統合カレンダーで見る」導線を追加

## 検証・Definition of Done

- `python scripts/verify_ui_styles.py` 系の算出スタイル実測＋headless Chromeプローブでの描画確認（calendar値を注入したスタブデータでレイヤー切替・ホーム除外ルールを検証）
- `node --check` / インラインJS構文確認
- 登録は dry-run→少数試行→一括の順。登録件数と結果の報告を残す
- `.env` の読み取り・値の出力をしない。fetch_notion.py の実行（外部API）は事前確認の上で行う
