## 1. アーキテクチャ

データ供給は「1ファイルの書き手は1人」の原則で **2系統** に分かれる。

```
系統A（団体のSNS発信）
[ registry.json ]    団体×媒体の元データ（人が編集して育てる）
        │  ① 読み込み
        ▼
[ /kotohira-news スキル (Claude Code) ]
        │  ② note等のRSSを WebFetch で取得（最新最大10件）
        │  ③ items / instagram / x を組み立て
        ▼  ④ 上書き保存
[ data.js ]          window.DASHBOARD_DATA（団体・SNS更新）

系統B（町のニュース／イベント／キャンペーン）
[ Notion 3DB ]       ニュースDB／イベントDB／キャンペーンDB
        │  ① 読み取り専用トークンでNotion API
        ▼
[ scripts/fetch_notion.py ]  Python標準ライブラリのみ・pip依存なし
        │  ② サムネ署名URLを assets/thumbs/ に保存し相対パス化
        ▼  ③ 上書き保存
[ notion-data.js ]   window.NOTION_DATA（news / events / campaigns）

              data.js ＋ notion-data.js
                       │  <script src> で両方読み込み
                       ▼
[ index.html ]   表示部（固定。9タブUIで描画）
                       │
                       ▼
       ブラウザ（ローカル / 将来は GitHub Pages）
```

**設計原則**: ロジック（表示HTML・スキル・スクリプト）とデータ（registry.json / data.js / notion-data.js）を分離。データ追加・更新でロジックを触らない。`data.js` と `notion-data.js` はそれぞれ生成元が1つに固定され、混線しない。

> 補足: NotionニュースDBへの収集の実体は別リポジトリの **konpie-bot**（Railway常駐・30分毎にRSS/スクレイプ→Discord→NotionニュースDB自動登録）。本リポジトリの `fetch_notion.py` は、そうして溜まったNotion 3DBを **読み取るだけ**（書き込み権限は持たせない＝最小権限）。

## 3. データモデル

### 3.1 registry.json（元データ）

```jsonc
{
  "project": "kotohira-news",
  "updated": "YYYY-MM-DD",
  "orgs": [
    {
      "name": "団体名",
      "summary": "概要",
      "channels": [
        { "type": "note", "url": "...", "rss": "https://note.com/{id}/rss",
          "auto": true, "verified": true, "note": "備考" },
        { "type": "instagram", "handle": "...", "url": "...",
          "auto": false, "verified": false }
      ]
    }
  ],
  "todo_orgs": ["未登録団体メモ"]
}
```

- `type`: `note` / `instagram` / `x` / `website` / `youtube` / `ameblo`
- `auto`: RSSで自動取得できるか。`verified`: URL/RSSを実取得で確認済みか。

### 3.2 data.js（表示データ・自動生成）

```jsonc
window.DASHBOARD_DATA = {
  "title": "琴平町 発信ダッシュボード",   // ※2026-07-09〜10以降 index.html では未使用（タイトルは静的HTML固定）
  "updated": "YYYY-MM-DD",              // ※同上。ヘッダーの「最終更新」表示自体を削除したため未使用
  "orgs": [
    {
      "id": "matatabi",                 // 安定キー（英数字）
      "name": "...", "summary": "...",
      "links": { "note":"", "instagram":"", "x":"", "website":"", "youtube":"", "ameblo":"" },
      "items": [                        // RSS由来。新しい順・最大10
        { "source":"note", "date":"YYYY-MM-DD", "title":"...", "url":"...", "thumbnail":"(任意)" }
      ],
      "instagram": [ "投稿URL", ... 最大2 ],   // 手動登録→埋め込み
      "x":         [ "投稿URL", ... 最大2 ]     // 手動登録→埋め込み
    }
  ]
};
```

- **団体タブ（ドリルダウン）** = 団体の `items` を表示（更新／Instagram／X サブタブ）。

### 3.3 notion-data.js（表示データ・自動生成 / 系統B）

`scripts/fetch_notion.py` が Notion 3DB から生成。スキーマの正は収集側 konpie-bot のコード。

```jsonc
window.NOTION_DATA = {
  "fetched": "YYYY-MM-DD HH:MM",     // 生成時刻
  "news": [                          // ニュースDB由来
    { "id":"", "title":"", "url":"", "summary":"", "org":"発信元",
      "media":"新聞|テレビ|行政|Webメディア|note|Instagram|X|HP|その他",
      "date":"YYYY-MM-DD", "thumbnail":"assets/thumbs/xxx.png",
      "duplicate":false,             // 同じ出来事の別媒体報道の可能性
      "pickup":false,                // Notion「定例で紹介」チェック。生成はされるが2026-07-09〜10以降は表示側で未使用（旧⭐定例ピックアップ機能は廃止）
      "show":true }                  // false のみ非表示（未定義は表示＝前方互換）
  ],
  "events": [                        // イベントDB由来
    { "id":"", "title":"", "url":"", "start":"YYYY-MM-DDTHH:MM", "end":"",
      "status":"実施前|実施中|終了",  // fetch_notion.py が開催日から算出。イベントタブの表示状態には使わず、front-endの eventDateStatus() を都度使う（下記参照）
      "city":"", "place":"",         // place は「開催場所」relation先ページのタイトルをresolve_place_namesが解決
      "address":"",                  // 「住所」ロールアップ（開催場所リレーション経由。get_any_text対応）
      "image":"assets/thumbs/xxx.jpg", "comment":"", "fee":"", "organizer":"" }
      // fee=「参加費（日本円）」(数値プロパティ)、organizer=「主催/運営」(マルチセレクト)。
      // どちらもget_any_text経由で取得（従来のget_rich_textでは型が合わず常に空だった不具合を修正）
  ],
  "campaigns": [ /* イベントDBと同一スキーマ（parse_event を共用） */ ]
};
```

- **ニュースタブ** = `news` を `date` 降順。`show!==false` のみ表示。最も新しい1件を⭐最新ニュースとしてフィーチャーカードで別立てし（`pickup`値は見ない）、直近2か月分を📋一覧・🗂ギャラリーで表示。
- **イベントタブ** = `events` を、front-end の共通関数 `eventDateStatus(it)` が開催日（`start`/`end`）から都度算出する状態（本日開催／開催中／開催予定／終了）で仕分ける。保存済み `status` は使わない（Notion側の値は取得時点で固定され、日付経過で古くなるため）。「終了」の一覧セクションは持たず、カレンダーから過去月に遡って詳細を開く。
- **キャンペーンタブ** = `campaigns` を、fetch_notion.py が算出した保存値 `status`（実施前・実施中・終了）で実施中・実施前（近い順）に整理して表示。「終了」の一覧セクションは廃止（カレンダー表示のみ）。
- イベントDBとキャンペーンDBは **完全同一スキーマ**（生成関数 `parse_event`/`fetch_events` を共用）。

**Notionプロパティとの対応（ニュースDB）**:
- `show` = チェックボックス「**表示対象**」。`fetch_notion.py` が `show=True` のニュースのみ出力する（例: 47件中16件）。ダッシュボードでどのニュースを見せるかをNotion側で人が制御できる。
- `pickup` = チェックボックス「**定例で紹介**」。DAO定例で取り上げる記事の目印として引き続き生成されるが、2026-07-09〜10のニュースタブ再構成（⭐最新ニュース→📋一覧→🗂ギャラリー）により表示側では参照しなくなった。
- ⚠️ `duplicate`（重複の可能性）は **現在のニュースDBにプロパティが存在しない**ため、`fetch_notion.py` は常に `false` を出力する（コードは将来のプロパティ追加を見越して残置。表示側の重複バッジ・薄め表示も実装済みだが現状は発火しない）。

**Notionプロパティとの対応（イベント／キャンペーンDB）**:
- 「開催場所」は会場DBへの **relation**。`fetch_page_title` がリンク先会場ページのタイトルを取得し、`resolve_place_names` が会場IDでキャッシュしながら `place` に埋める（会場ページがインテグレーションに未共有＝404の場合は空にフォールバックし、イベント表示自体は止めない）。会場DBにも別途インテグレーションのコネクトが必要。
- 「住所」は上記relation経由の **rollup**。`get_any_text` が対応し、会場を紐づければ自動で `address` に入る。
- 「参加費（日本円）」（数値型）・「主催/運営」（マルチセレクト）は、型に依存せず平文を取り出す新設関数 `get_any_text`（rich_text/number/select/multi_select/formula/rollupに対応）で取得する。従来の `get_rich_text` では型が合わず全件空になっていた不具合を修正済み。

### 4.1 表示形式の設計方針（参考サイト調査の反映）

`docs/参考サイト調査.md`（他地域サイト10件のUI調査）の総括を踏まえ、**情報の性質で表示形式を変える**方針を採用（城崎温泉の事例）。純ニュースは流し読みできるリスト、催し・お得情報・注目トピックは写真カードで見せる。
一方、海士町由来の「カード⇄リスト切替＋フィルタチップ」は**あえて実装しない**判断（小規模・件数が多くないため導線を増やすより素直な一覧を優先）。詳細は同調査の末尾「redesign3への反映」を参照。

## 6. 更新フロー（運用）

**系統A（団体SNS更新 / data.js）**
1. `registry.json` に団体・媒体・（必要なら）IG/X投稿URLを追記。
2. Claude Code で `/kotohira-news` 実行 → `data.js` 再生成。

**系統B（ニュース／イベント／キャンペーン／体験・滞在 / notion-data.js）**
1. Notion 3DB（+体験・滞在DB）が最新であること（ニュースDBへの収集は konpie-bot が常時実施）。
2. `python scripts/fetch_notion.py` を実行 → `notion-data.js` 再生成＋サムネを `assets/thumbs/` に保存。
   - 一部DBがコネクト漏れ等で404でも、成功したDBだけ更新し失敗DBは既存内容を温存。
   - 体験・滞在DBは環境変数 `EXPERIENCE_NOTION_DB_ID` を設定した場合のみ取得対象になる（未設定時は `experiences` が空でプレースホルダ表示）。
   - イベント／キャンペーンの「開催場所」は会場DBへのrelationのため、会場DBにも別途インテグレーションのコネクトが必要（未共有ページは404扱いで空にフォールバック）。

**系統C（🔗リンクタブ / links-data.js・手編集）**
1. Notion連携ではなく `links-data.js` を直接編集する（掲載ルール・画像の出所ルールはファイル冒頭コメントを参照）。
2. サムネ画像は `assets/links/` にローカル保存（local-first。出所は自作/撮影/先方提供、または各サイトのog:imageのみ。スクリーンショットは不可）。
3. SNS採用の裏取りは `docs/公式SNSアカウント調査.md` に記録する。

**系統D（🍜うどん店／🅿駐車場 / udon-data.js・parking-data.js）**
1. CSV・現地情報を入口に、公式サイト/SNS、行政・観光公式を優先してWeb照合する。
2. `checked` と各項目を手編集し、未確認値は推測せず「要確認」にする。閉業・移転等は削除せず `show:false` で保留する。

**共通**
4. 表示部（`index.html`）を開く（将来は push で Pages 更新）。
